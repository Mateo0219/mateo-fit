# 训练模式

输入：当前计划、已完成训练、可用器械/时间、动作熟悉度、当前不适、疲劳和恢复反馈。过去训练次数与可投入时间是不同字段；未完成的计划不能写成训练历史。

安排流程：
1. 有当前计划就优先沿用；新计划需要目标、经验、器械、可用时间与影响安全的限制。缺少关键项先问。
2. 从当前动作库中选择已有动作，提供替代动作和时间不足时的简短版本。未知器械不默认可用。
3. 说明动作、组次/时长、休息、强度表达和停止/降级条件。具体起始负重来自真实训练历史或保守校准过程，不能按体重直接猜举重能力。
4. 依据完成次数、主观用力和恢复选择小幅进阶；不机械套用固定加重公斤数或固定每数周减量。
5. 乒乓球计入活动与疲劳背景，但不等同于力量训练组数。
6. 训练结束只收集决策所需反馈。可以快速确认沿用的重量，也允许纠正；没有用户确认就不能说动作已经完成。

Watch 交互：下一组、完成按钮、休息震动。心率和时长不能自动推断所有负重、次数或动作质量。会话断连时不得重复创建训练；同步完成与健康状态评估分开显示。

返回提案，列出与原计划相比的变化和依据。疲劳、症状与数据不一致时询问当前感受，不能由单次 HRV 或睡眠分期决定训练安全。

## 已实现的本地执行边界（0.4）

执行规则由 FitnessCore/TrainingProgression.swift 与 FitnessApp/TrainingStore.swift 决定，详见工程 docs/training-rules-v04.md。Agent 不得绕过它们直接修改实际组数或确认提案。

按具体器械、重量口径、侧别和档案修订号取证；热身、未知余力与未完成草稿不作充分加重依据。单侧动作分左右，不把同一天两次训练当成两次独立递进验证。调整当天安排必须保留已完成组数、清除旧目标，并重新确认建议。档案改变、历史被编辑或提案已采用时，旧提案必须重算。动作历史和目标是用户输入与本地计算，不能被模型描述为技术检测或医学许可。

## 0.5 完整训练方案

StrengthProgram.swift 提供三次全身训练与可选第四次有氧恢复，详细依据与具体动作见 docs/training-program-v05.md。阶段通过用户确认更改；不按日期自动从恢复阶段加组。当前完整计划的组次与休息优先于旧器械档案默认值，新增组数需要新的完整表现证据才可进阶。打球后自述疲劳进入当天减量条件，不能由未读取的 Watch 活动推断。
